The doze add postgres in the header is doze 0.2. On 0.1.1, write the block by hand (below).

The newest release, 0.2.5, needs doze 0.2.0. 0.2.4 runs on your 0.1.1.

Both run Postgres 14 to 18. 0.2.5 is the newest; 0.2.4 is the newest your doze can run. Pick a path below. Neither touches your data.

0.2.5 carries doze: "0.2.0" in its signed index entry; every release before it sets no minimum.

Update doze

Recommended

1Update

doze 0.1.1 is the CLI: update it with Homebrew
$ brew upgrade doze

Update doze first, then move the pin: 0.1.1 can't check a release's minimum, so its doze modules upgrade would take 0.2.5 anyway. Want the Mac app too? brew install --cask doze-dev/tap/doze; it updates itself from Settings › About.

2Update doze.hcl

doze 0.2 names every line to change. Each block gains module; idle_timeout becomes sleep, and the default sleep is 2 minutes (was 5).

doze.hcl
- postgres "postgres" {
+ module postgres "postgres" {
    version = 18
  }

What you get

  • postgres 0.2.5, and 0.3 with extensions by name when it lands. What changed in 0.2.5
  • doze add, doze migrate between Postgres majors, and the desktop app.
  • From then on, doze picks a release your doze can run, by itself.
  • Every example on the overview works as written.
then, in your project
$ doze modules upgrade postgres
  moves doze/postgres 0.2.4 → 0.2.5 in doze.lock; commit it

Stay on 0.1.1

Use postgres 0.2.4

From doze 0.2 this happens on its own: doze skips releases that need a newer doze and pins the newest one that runs. doze 0.1.1 came before releases carried a minimum, so it would fetch 0.2.5. Hold postgres at 0.2.4 yourself, in 0.1.1's own syntax:

If you don't: doze 0.1.1 fetches 0.2.5 anyway

[what happens then: to test]

1Hold the release in doze.hcl

doze.hcl, as doze 0.1.1 reads it
modules {
  module "postgres" { version = "0.2.4" }
}

postgres "postgres" {
  version = 18
}

When you do update: delete the modules block. doze 0.2 refuses it ("the modules block is gone") and pins releases itself.

What doze 0.2 and later print

From 0.2 on, doze checks each release's minimum. When the next minimum arrives, say a future release that needs doze 0.3.0 while you are on 0.2.0, it says so in one of two ways, word for word:

Nothing in the registry runs on this doze
$ doze up
error: postgres 18 needs doze 0.3.0 or newer; this doze is 0.2.0. Update doze (in the app: Settings › About), then run the command again
Why
doze looked for a postgres release that supports Postgres 18 and runs on your doze, and none does. It names the oldest doze that would work.
Fix
Update doze: brew upgrade doze, or Settings › About in the app. Run the same command again; nothing else to undo.
doze.lock was written by a newer doze
$ doze up
error: module doze/postgres [0.x.y] (pinned in doze.lock) needs doze 0.3.0 or newer; this doze is 0.2.0. Update doze (in the app: Settings › About); the lock was written by a newer doze
Why
A teammate on a newer doze committed doze.lock with a release that needs it. The pin is the team's agreement, so doze will not quietly run something older.
Fix
Update doze to match your team. Don't edit the pin down: the next commit would move everyone else back too.
