Publish a module

A module teaches doze to run one more engine. Here is what it takes to write one, release it, and get it signed, with the rules the registry enforces.

Status, honestly

Today the registry publishes doze-dev's own modules. Outside publishers: planned

doze has one registry and one namespace, doze. Any other namespace is refused: module namespace "acme": doze has one registry, and its modules are all under "doze"

What you can do today
works

Run your own module, unpublished. DOZE_HTTPD_PLUGIN=./bin/httpd-plugin doze up skips the registry and the lock for that type. Teams run private modules this way.

works

Contribute it to doze-modules. A pull request to doze-modules; once merged, CI builds it and the registry signs it as an official module.

01

What a module is

A plugin binary, written in Go with doze-sdk, that speaks the doze plugin protocol over gRPC. doze is an engine-blind host: proxy, supervisor, config, lockfile. Everything engine-specific lives in the module: how to find the engine binary, set up its data directory, start it, tell when it is ready, and what its config block accepts. Official modules get no special path; this is the Terraform provider model.

Self-contained

The plugin is the server. doze AWS and doze Kafka work this way, as does the template's httpd. No version =.

Real upstream engine

The module fetches a real binary (Postgres, Valkey) from doze-binaries and declares the engine majors it supports.

Testing, per engine major

Three layers, each catching what the one before cannot. The registry's "tested on every listed engine major" tick means the third layer ran green on each major in Versions.

every go test

Decode tests

Defaults, error messages, version gates, and that an unknown attribute is an error.

-tags acceptance

enginetest

Boots a real engine from your driver and checks that declared roles, buckets and extensions converge, twice. Skips without DOZE_<ENGINE>_BINDIR.

before release

The real thing

DOZE_<TYPE>_PLUGIN=… doze up, then doze lint, doze status and a real client. Ten seconds.

Acceptance, once per engine major
$ export DOZE_POSTGRES_BINDIR=$PWD/backend/bin   # Postgres 17 here; repeat for 14 … 18
$ go test -tags acceptance -timeout 20m ./...
05

Releasing: archives, hashes, signatures

The SDK's modtool builds a release the same way for you as for the official modules. You build; the registry signs, because the key lives there.

Terminal
$ go run ./cmd/release --version 0.1.0
dist/httpd/
  httpd-plugin-0.1.0-aarch64-apple-darwin.tar.gz
  httpd-plugin-0.1.0-aarch64-unknown-linux-gnu.tar.gz
  httpd-plugin-0.1.0-x86_64-unknown-linux-gnu.tar.gz
  index.yaml   # protocol, engines, doze, sha256 per archive; unsigned
  meta.yaml    # the docs, from Describe()

Bump for every change

Users' locks pin your releases. A fix, a new argument, a new engine major: each is a new version.

Never rebuild a release

Rebuilding a published version with different bytes is refused:

httpd 0.1.0 (aarch64-apple-darwin) is already published with a different sha256 — bump the module version instead of rebuilding it

Keep every old release

Merge your previous index.yaml before building, so last year's locks and older doze versions keep resolving. The registry's CI refuses to drop one.

06

Declaring the oldest doze your release needs

The plugin protocol number says the wire is the same. It does not say which doze has everything your module leans on. Each release can carry a doze field: the oldest doze that runs it.

index.yaml · one release
releases:
  "0.2.5":
    protocol: 1
    engines: ["14", "15", "16", "17", "18"]
    doze: "0.2.0"        # oldest doze that runs it
    artifacts: …

Where the value comes from

You don't type it. modtool stamps it from the SDK you built with (proto.MinHost). doze-sdk v0.11.0 and later stamp "0.2.0": modules built with it leave fetching engine binaries to doze, which only doze 0.2.0 and later do.

Format is three numbers. npm run validate rejects anything else: doze must be the oldest doze version that runs it, as "0.2.0"

How doze uses it

choosing a release

Releases that need a newer doze are skipped; an older release that fits is chosen instead. If none fits, doze says so:

postgres 17 needs doze 0.3.0 or newer; this doze is 0.2.0. Update doze (in the app: Settings › About), then run the command againdoze 0.2 and later. The 0.3.0 release is an example, to show the shape.
reading doze.lock

The pin keeps the field, so a teammate on an older doze is told why rather than failing at launch:

module doze/postgres 0.3.1 (pinned in doze.lock) needs doze 0.3.0 or newer; this doze is 0.2.0. Update doze (in the app: Settings › About); the lock was written by a newer dozedoze 0.2 and later. doze 0.1.1 cannot read the field: update doze before doze modules upgrade.

When to raise it

  • You move to a doze-sdk whose MinHost is higher: it rises on its own. Say so in your release notes.
  • Your module starts using a newer protocol feature or SDK field that an older doze ignores or lacks. [An override in modtool.Module for this case does not exist yet] new
  • Never lower it on a published release; it is part of the release, like its bytes.

postgres 0.2.5 and the other 3 Nov 2026 releases are the first to carry it ("0.2.0"); earlier releases have no field and run on any doze. Today it sits outside the signed part of the index; the design moves it inside (known gaps).

How outside publishing will work

Your modules under your name, signed with your key, with the same checks doze applies to its own. doze-dev never holds your key.

  1. Claim a namespaceProve you control a GitHub user or org of the same name. Modules live at yourname/module.
  2. Make your keynpm run keygen yourname already exists in doze-registry. The private half stays in your CI.
  3. Sign in your CIRelease with modtool as above; your CI signs each archive and the index.
  4. Pinned on first useA user's first resolve records your key in their doze.lock. A later change is a hard error until they clear the pin.
  5. Get verifiedOptional: prove a domain with a DNS TXT record naming your key.
  6. What users seeNothing new: your module resolves, verifies and pins like an official one, and moves only on doze modules upgrade.

Three tiers

Official

Namespace doze. Built from doze-dev repos, key compiled into doze. The only tier that exists today.

Verified

A proven publisher. Namespace tied to a domain by DNS. Key pinned on first use. planned

Community

Anyone with a namespace. Signed and pinned like the others; no identity claim beyond GitHub. planned
